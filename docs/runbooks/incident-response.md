# Incident Response Runbook

**Version:** 1.2  
**Owner:** SOC Platform Team  
**Last Updated:** 2024-01-15  
**Applies To:** All AI Agent SOC incidents (severity LOW through CRITICAL)

---

## Overview

This runbook defines the end-to-end incident response lifecycle for security incidents detected by the AI Agent SOC platform. It covers five phases: **Detect**, **Triage**, **Investigate**, **Remediate**, and **Close**.

All incidents are tracked in the SOC platform at `/api/v1/incidents`. Severity definitions:

| Severity | CVSS Equivalent | SLA (Detection → Notification) | SLA (Notification → Resolution) |
|----------|-----------------|-------------------------------|----------------------------------|
| CRITICAL | 9.0–10.0 | 5 minutes | 4 hours |
| HIGH | 7.0–8.9 | 15 minutes | 24 hours |
| MEDIUM | 4.0–6.9 | 1 hour | 72 hours |
| LOW | 0.1–3.9 | 4 hours | 2 weeks |

---

## Phase 1: Detect

### 1.1 Automated Detection

The SOC platform automatically creates incidents when:
- A CRITICAL or HIGH severity CloudEvent is received and the triage agent assigns verdict `TRUE_POSITIVE` with confidence ≥ 0.85.
- A pattern of MEDIUM events from the same `principal_id` is detected within a rolling 1-hour window (correlation rule: ≥ 3 distinct event types).
- A threat hunt returns results matching a known IOC.

**Incident creation notification:** PagerDuty alert is fired via the `soc-incidents` integration key. The on-call analyst receives a push notification within 60 seconds.

### 1.2 Manual Detection

An analyst may manually create an incident via:
```bash
curl -X POST https://soc.internal/api/v1/incidents \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Tenant-ID: $TENANT" \
  -d '{
    "title": "Suspected credential theft - agent-prod-042",
    "severity": "HIGH",
    "source_event_id": "evt-abc123",
    "description": "Analyst observed anomalous IAM calls..."
  }'
```

### 1.3 Detection Verification Checklist

- [ ] Incident ID assigned (format: `INC-XXXXXXXX`)
- [ ] Source event ID linked
- [ ] Severity correctly assessed
- [ ] Correct tenant context
- [ ] PagerDuty alert acknowledged within SLA

## Phase 2: Triage

**Goal:** Determine if the incident is a True Positive, False Positive, or requires escalation. Target: < 15 minutes for CRITICAL, < 1 hour for HIGH.

### 2.1 Initial Assessment

1. **Review the SOC triage summary** generated by the AI agent:
   ```bash
   curl -H "Authorization: Bearer $TOKEN" \
     https://soc.internal/api/v1/incidents/$INC_ID
   ```
   Review: `analysis`, `verdict`, `mitre_techniques`, `citations`, `severity_score`.

2. **Check the source event** for context:
   - `principal_id`: Which AI agent triggered this?
   - `source_repo`: Which system component?
   - `mitre_techniques`: What ATT&CK techniques are implicated?

3. **Review recent events from the same principal** (last 24h):
   ```bash
   curl -H "Authorization: Bearer $TOKEN" \
     "https://soc.internal/api/v1/events?principal_id=$PRINCIPAL&hours=24"
   ```

### 2.2 Verdict Decision Tree

```
Is the event signature unambiguously malicious?
├── YES → TRUE_POSITIVE → Proceed to Investigate
└── NO
    ├── Is the behavior explicable by authorized activity?
    │   ├── YES → FALSE_POSITIVE → Document and Close
    │   └── NO
    │       ├── Confidence < 0.75 → NEEDS_REVIEW → Assign to senior analyst
    │       └── Confidence ≥ 0.75 but context missing → ESCALATED → Engage Asset Owner
```

### 2.3 Update Incident Status

```bash
# Confirm as True Positive
curl -X PATCH https://soc.internal/api/v1/incidents/$INC_ID \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"status": "IN_PROGRESS", "verdict": "TRUE_POSITIVE", "assignee": "analyst@example.com"}'

# Mark as False Positive
curl -X PATCH https://soc.internal/api/v1/incidents/$INC_ID \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"status": "RESOLVED", "verdict": "FALSE_POSITIVE", "resolution_notes": "Authorized maintenance activity - Change CHG-2024-0892"}'
```

### 2.4 Triage Checklist

- [ ] Incident status updated to `IN_PROGRESS` or `RESOLVED`
- [ ] Verdict assigned (`TRUE_POSITIVE`, `FALSE_POSITIVE`, `NEEDS_REVIEW`, `ESCALATED`)
- [ ] Assignee set
- [ ] For FALSE_POSITIVE: root cause documented to improve detection rules

## Phase 3: Investigate

**Applies to:** TRUE_POSITIVE and ESCALATED incidents only.

### 3.1 Scope Determination

Determine the blast radius:

1. **Identify affected principals:**
   ```bash
   # Search for all events from this principal in the last 7 days
   curl "https://soc.internal/api/v1/events?principal_id=$PRINCIPAL&days=7&severity=HIGH,CRITICAL"
   ```

2. **Check for lateral movement indicators:**
   - Multiple principals appearing in events within a short timespan
   - Events across multiple source repositories from the same principal
   - IAM role assumption chains

3. **MITRE ATT&CK technique analysis:**
   - Review the `mitre_techniques` array on the incident
   - For each technique, check if prerequisites (earlier-stage techniques) are also present

### 3.2 Evidence Collection

Collect and preserve the following before any remediation:

```bash
# Export all events related to this incident
curl "https://soc.internal/api/v1/incidents/$INC_ID/evidence" \
  -H "Authorization: Bearer $TOKEN" > evidence-$INC_ID.json

# Export OpenSearch raw events (for CRITICAL incidents)
# Use the OpenSearch Dashboards export or the hunting endpoint:
curl -X POST "https://soc.internal/api/v1/hunt/launch" \
  -H "Authorization: Bearer $TOKEN" \
  -d "{\"hypothesis\": \"Evidence collection for $INC_ID\", \"hunt_type\": \"INCIDENT\", \"incident_id\": \"$INC_ID\"}"
```

Store evidence in the designated S3 evidence bucket: `s3://soc-evidence-${TENANT}/${INC_ID}/`

### 3.3 Timeline Reconstruction

Build an attack timeline documenting:
- T+0: Initial event (use CloudEvent `time` field, not processing time)
- Subsequent events in chronological order
- First alert time
- Analyst notification time
- Containment time

Update the incident timeline via PATCH:
```bash
curl -X PATCH https://soc.internal/api/v1/incidents/$INC_ID \
  -d '{"timeline": [{"time": "...", "event": "Initial compromise detected", "source": "INC-EVENT-001"}]}'
```

### 3.4 Investigation Checklist

- [ ] Affected principals and systems identified
- [ ] Evidence preserved in S3
- [ ] Attack timeline constructed
- [ ] MITRE ATT&CK kill chain mapped
- [ ] Remediation steps identified
- [ ] Legal/compliance notified if PII or regulated data involved

## Phase 4: Remediate

### 4.1 Containment Actions

Execute containment actions appropriate to the incident type:

**Identity / Access violations:**
```bash
# Revoke compromised agent credentials via identity governance API
curl -X POST https://identity-governance.internal/api/v1/principals/$PRINCIPAL/revoke \
  -H "Authorization: Bearer $BREAK_GLASS_TOKEN" \
  -d '{"reason": "SOC incident $INC_ID", "scope": "all"}'
```

**Runtime anomalies:**
```bash
# Quarantine agent pod
kubectl label pod $POD_NAME quarantine=true -n $NAMESPACE
kubectl annotate pod $POD_NAME soc.incident-id=$INC_ID
```

**Supply chain compromises:**
```bash
# Block compromised package version
curl -X POST https://supply-chain.internal/api/v1/blocklist \
  -d '{"package": "$PACKAGE", "version": "$VERSION", "reason": "$INC_ID"}'
```

### 4.2 Eradication

After containment:
1. Remove malicious resources (revoke tokens, delete backdoor accounts, remove malicious packages)
2. Patch or remediate the vulnerability that allowed the initial compromise
3. Rotate all secrets accessible to the compromised principal

### 4.3 Recovery

1. Restore affected services from clean state (last known-good deployment)
2. Re-enable the affected principal with new credentials (if appropriate)
3. Verify normal operation via health checks and smoke tests
4. Monitor for recurrence for 48 hours post-recovery

### 4.4 Remediation Checklist

- [ ] Containment action executed and verified
- [ ] Eradication complete
- [ ] Secrets rotated where necessary
- [ ] Recovery verified
- [ ] Monitoring extended for 48h post-recovery

## Phase 5: Close

### 5.1 Resolution Documentation

```bash
curl -X PATCH https://soc.internal/api/v1/incidents/$INC_ID \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "status": "RESOLVED",
    "resolution_notes": "Root cause: ...\nActions taken: ...\nPrevention: ...",
    "remediation_steps": ["Step 1: ...", "Step 2: ..."],
    "tags": ["post-mortem-required"]
  }'
```

### 5.2 Post-Incident Review (PIR)

Required for all CRITICAL incidents and HIGH incidents with MTTR > SLA:

1. Schedule PIR meeting within 5 business days
2. PIR template: `docs/templates/post-incident-review.md`
3. Document: timeline, root cause, impact, what went well, what to improve, action items
4. Publish PIR to the SOC wiki within 10 business days

### 5.3 Metrics Update

After closure, the following metrics are automatically updated:
- MTTD (Mean Time to Detect)
- MTTC (Mean Time to Contain)
- MTTR (Mean Time to Resolve)
- False Positive Rate

These feed the security posture score via the `posture/score` endpoint.

### 5.4 Close Checklist

- [ ] Incident status set to `RESOLVED` or `CLOSED`
- [ ] Resolution notes complete
- [ ] Post-incident review scheduled (if required)
- [ ] Lessons learned captured
- [ ] Detection rules updated to prevent recurrence
- [ ] Posture score refreshed: `POST /api/v1/posture/score/refresh`
